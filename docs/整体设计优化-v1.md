## 一、14 处优化（按收益排序）

### 1. 取消"每周重置"，周数据全部派生 ★最高收益

**现状/原设计**：`kid_profile` 上存 `week_stars`、`week_achieved`，需要定时任务在周一清零。
**问题**：重置任务一旦漏跑或跑两次，数据就永久错；且"本周"与"本周任务"两套口径容易不一致。

**优化**：

```sql
-- 本周星星（派生）
SELECT COALESCE(SUM(amount),0) FROM star_ledger
WHERE child_id=$1 AND local_date >= $weekStart;

-- 本周达标数（派生，任务本身按 week_start 分组）
SELECT COUNT(*) FROM tasks
WHERE child_id=$1 AND week_start=$weekStart AND is_achieved;
```

只保留 `available_stars`（可用余额）与 `total_stars`（累计）两个存储字段，二者由 `star_ledger` 事务内同步维护。
**删掉 `week_stars` / `week_achieved` 两个字段与对应的重置逻辑。**

### 2. 事件表优先，计数由事件推导

**问题**：现在 `tasks.current_count`、`egg.is_completed`、`mood` 是否有加星，都是"就地改状态"，没有事件，无法审计、无法解释"这 3 颗星哪来的"。

**优化**：所有"动作"都落**事件表**：

| 事件表 | 记录什么 |
| --- | --- |
| `task_checkins` | 每次 +1 次打卡（task_id, delta, at, local_date） |
| `egg_opens` | 每天每个彩蛋的开启（def_id, local_date） |
| `usage_sessions` | 每次使用时长（started_at, ended_at, minutes） |

`current_count` 保留为**冗余缓存**（读得快），但可随时由事件重算；`is_achieved` 改为派生（`current_count >= target_count`）或由事件触发一次性写。

**收益**：周报、趋势、AI 工具、家长审计全部有数据可查；赔偿/纠错也能定位。

### 3. 幂等键统一

**问题**：孩子连点两下 `+1`、网络重试、家长重复提交兑换 → 重复加星。

**优化**：所有写接口带 `Idempotency-Key`（客户端 UUID），服务端在 `star_ledger.idempotency_key` / `task_checkins.idempotency_key` 上做唯一约束；重复请求直接返回上次结果。

### 4. 时间处理单点化

**问题**：`getWeekStart()` 在三个 service 各写一份，且用 `toISOString()`（UTC）——东八区周一 0–8 点会算成上周。

**优化**：`server/common/time.ts` 单点提供：

```ts
todayInTz(tz = 'Asia/Shanghai'): string           // 'YYYY-MM-DD'
weekStartOf(date, weekStartDay = 1): string
nowIso(): string
```
所有业务代码禁止直接 `new Date().toISOString().slice(0,10)`。

### 5. 模板与种子单点化

**问题**：默认任务在 `auth.service`（6 项）、`kid.service`（4 项且预置了进度 2/1）、商店在 `shop.service`（6 项，含"1⭐=1元"违规文案）——三份不一致。

**优化**：`server/config/templates.ts` 单点定义 `TEMPLATES[ageBand]`；**引导预览页与写入使用同一份数据源**（同一个函数产出）。

### 6. AI 工具层复用业务 Service

**问题**：`chat.service.buildDataContextRaw()` 自己写 SQL 查 8 张表，与业务 service 两套逻辑，必然漂移。

**优化**：`get_today_snapshot` 等工具内部**直接调用** `TasksService/ReadingService/...` 的方法；禁止工具层独立写查询。

### 7. 双端共享数据层，只分壳

**问题**：如果孩子端与家长端各写一套 API，字段与口径会分叉。

**优化**：一套 REST API，按 `childId + scope(kid|parent)` 返回不同字段；两端只分 shell 与组件密度。家长端多了"审计/导出/配置"接口，但读取数据的接口是同一批。

### 8. 用 react-query 管服务端状态

**问题**：现在 `AppContext` 手写缓存 + 乐观更新（且乐观更新用了闭包里的旧 profile），等于自己造一个不完整的缓存层。

**优化**：
- `@tanstack/react-query`（已在依赖里）负责拉取、缓存、失效、重试
- `FamilyContext` 只管两件事：`children[]` 元数据 + `currentChildId`
- `ParentModeContext` 只管家长门状态
- 星星加减用 `useMutation` + `onMutate` 乐观更新，`onSettled` 以服务端返回为准

### 9. 数字只在一个地方解释

**问题**：顶部四个数字卡（可用/累计/本周/达标）对 6–10 岁无意义，而且四处在解释同一件事。

**优化**：孩子端只有**宝箱进度**（图形）；任何"数字问题"统一去「我的 → 我的星星账本」（流水式）。家长端保留完整数字。

### 10. 渐变面积收敛

**问题**：现在几乎每个页面顶部都是大面积粉紫渐变 + 白字，实测 2.24:1 不可读，且长页面渐变显脏。

**优化**：渐变**只用于两处**——孩子端头图（浅渐变 + `#2E1065` 深字）与主按钮（深渐变 + 白字）。其余全部浅底白卡。

### 11. 页面收敛：8 页保留，但"层级"重排

| 页面 | 位置 | 变化 |
| --- | --- | --- |
| 本周 | 导航 1 | 主入口 |
| 阅读 | 导航 2 | — |
| 动起来 | 导航 3 | — |
| 说说话 | 导航 4 | — |
| 我的 | 导航 5 | 新增（替代"家长"） |
| 商店 | 首页卡片 | 降级为二级入口 |
| 闯关 | 首页卡片 | 降级 |
| 签到 | 首页卡片 | 降级 |
| 家长端 | 齿轮 + 家长门 | 独立 shell，不占导航 |

**页面数不变、导航减少 2 格**，误触率与认知负担同步下降。

### 12. P0 从 10 项压到 7 项

| 原项 | 处理 | 理由 |
| --- | --- | --- |
| P0-0 多孩地基 | **保留（前置）** | 不清则全返工 |
| P0-6 配置中心 | **保留（前置）** | 家长定义一切的前提（可砍到"任务+商店+奖励"三项） |
| P0-7 家长门 | **保留（前置）** | 合规硬要求 |
| P0-8 使用管理 | **保留（前置）** | 合规硬要求 |
| P0-1 奖励可见 + 庆典 | 保留 | 核心体感 |
| P0-2 AI 日报 | 保留 | 差异化 |
| P0-3 心愿单 | 保留 | 长效目标 |
| P0-4 家长周报 | **降级**：P0 做"文字版周报"，图片导出放 P1 | 图片渲染是独立工程量 |
| P0-5 闯关记录 | 保留（纯文案 + 图标改造） | 成本极低 |
| P0-9 内驱三支柱 | **移到 P1** | 需要新交互，且依赖 P0-1 落地后观察 |

**P0 七项**：多孩地基 · 配置中心 · 家长门 · 使用管理 · 奖励可见+庆典 · AI 日报 · 心愿单。（闯关改造作为 P0-5 的"顺手项"合并进配置中心那批）。

### 13. 状态机显式化

每个有状态的实体定义状态机，禁止"跳过状态"：

```
任务：pending → in_progress → achieved ──(跨周)──> archived
心愿：pending(孩子提) → priced(家长定价) → claimable(攒满) → claimed(兑现)
会话：active → idle(10min) → closed(压缩触发)
使用：active → resting(强制休息) → locked(超时长/睡眠时段)
```

### 14. 统一错误与离线层

- 所有写操作走 `useMutation` 统一错误处理 → 映射到儿童化文案
- 打卡/心情等"可离线"操作进入本地队列（localStorage），恢复后按 `Idempotency-Key` 补交
- 服务端统一 `{ ok, data, error: { code, message, retryable } }`，前端只认 `retryable` 决定是否给"再点一次"

## 二、需要拍板的三处张力（我给建议，标注默认）

| 张力 | 选项 | 建议 |
| --- | --- | --- |
| 签到是独立页还是首页模块 | A 独立页（现状）／B 首页展开模块 | **A**，但首页卡片给状态摘要（今日 2/4）；独立页便于深链与埋点 |
| 心愿是否需要家长"审批文案" | A 只定价／B 定价 + 可选留言 | **A** 先做，留言放 P1（家长留言对孩子价值高但交互成本也高） |
| 二孩是否显示"本周对比" | A 不显示／B 家长端折叠 | **B**，但默认收起，需要点一下才展开 |

## 三、优化后的整体结构（一页看清）

```
┌ 登录/引导（一次性） ────────────────────────────────┐
│ 同意 → 孩子信息(头像/昵称/年龄) → 模板+预览 → 家长门 → 使用管理 │
└──────────────────────────────────────────────────┘
                        ↓
┌ 选人页（≥2 孩子） ────────────────────────────────┐
└──────────────────────────────────────────────────┘
        ↓                                  ↓
┌ 孩子端（无锁，5 tab）┐          ┌ 家长端（家长门后）──────┐
│ 本周 阅读 动起来      │          │ 概览 · 周报 · 孩子管理    │
│ 说说话 我的          │          │ 任务 · 奖励 · 商店心愿     │
│ 商店/闯关/签到=首页卡片│          │ 记录 · 设置（时长/PIN/边界）│
└──────────┬──────────┘          └──────────┬────────────┘
           │                                 │
           └──────── 共用一套 API/数据层 ──────┘
                        ↓
   ┌── 事件表（打卡/彩蛋/使用）── star_ledger（唯一星星真相）
   └── 派生：本周星星/达标/进度/趋势/报告
                        ↓
              AI 工具层（只读，复用业务 Service）
                        ↓
         AgentLoop（≤3 步）+ 分层记忆（L0 原文/L1 摘要/L2 画像）
```

## 五、判断标准（用来拒绝后续需求）

> 需要"每周重置一次数据"的功能，都是设计错误。
> 需要"再存一个计数字段"的地方，先问能不能从事件推导。
> 需要孩子读数字才能理解的界面，都是还没设计完。
> 需要两套 API 才能实现的两端，是同一件事被重复做了一遍。
